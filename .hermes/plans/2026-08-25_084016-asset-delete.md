# Asset Delete Feature — Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Let admins permanently delete an asset from the register via a guarded in-page dialog, with the deletion mirrored to SharePoint and recorded in the audit trail.

**Architecture:** Re-introduce `XanaSupabase.deleteAsset(id)` (removed in the ponytail cleanup once it had zero callers — now it has a purpose). The DB already handles everything hard: a BEFORE DELETE trigger writes the SharePoint-sync outbox row (migration 0002), and the asset_history audit trigger records the delete op (migration 0014). So the client work is UI-only: a danger dialog on the asset detail card, gated to admin/super_admin roles, using the same `showDialog` pattern Admin uses. RLS on assets already allows deletes for admin/super_admin (migration 0016 policies).

**Tech Stack:** Vanilla JS in `assets/index.html`, adapter function in `js/supabase-client.js`, no new dependencies, no migrations.

---

## Current Context (verified)

- **DB is delete-ready.** Migration 0002's trigger fires BEFORE DELETE on assets, enqueues a `delete` op into `sharepoint_sync`, and pg_cron retries it; migration 0014's audit trigger logs the delete with actor + snapshot. No FK blocks: `asset_events.item_id` and `asset_history.item_id` are plain text columns without FK constraints, so history/events survive as an archive after the asset row is gone (deliberate — chain-of-custody outlives the record).
- **RLS:** super_admin bypasses; scanner-role updates allowed but DELETE policy is admin/super_admin only (migration 0016). Non-admins will get a 401-ish error from PostgREST — the UI must gate on role first so they never see the button.
- **Adapter:** `deleteAsset` was deleted from `js/supabase-client.js` in commit 7043d8b (ponytail cleanup). It needs re-adding (~5 lines).
- **UI:** detail card action row lives in `showDetail()` at `assets/index.html` ~line 376 (`detail-actions` div). Roles available in scope via `myRoles()` result — check how `startApp()` stores them; if roles aren't retained in a module variable, capture them at boot.
- **Precedent for dialogs:** Admin page has `showDialog({title,body,confirmText,danger,onConfirm})` + `toast()` in `admin/index.html` ~lines 269–317. Assets page does not have these helpers yet — copy them over (small duplication acceptable across pages; extracting to a shared file is YAGNI until a third page needs it).
- **SharePoint mirror:** delete ops flow through the same outbox → `api/sharepoint-sync.js` path as inserts/updates (verified working in E2E earlier this session).

## Design decisions

1. **Hard delete, not soft.** Requirements doc treats disposal/retirement as a *status* ("Retired" exists in choices). Delete = "this row should never have existed / test data". Keep both paths.
2. **Admin-only visibility.** The button renders only when caller has `admin` or `super_admin` role.
3. **Confirm dialog shows tag + serial** so the user can verify they're deleting the right physical item — tags are now guaranteed unique so there's no ambiguity.
4. **Toast on success** ("Asset XL-nnn deleted") matching admin patterns.

    title:"Delete asset",
    body:"Permanently delete <b>"+esc(current.tag)+"</b> (serial "+esc(current.serial||"—")+")? "

## Risks / Tradeoffs / Open Questions

- **Deletion is permanent.** Mitigated by: confirm dialog naming tag + serial, admin-only gating, audit trail preserving who-deleted-what, and events/history tables retaining archives. If accidental deletions become a worry later, a soft-delete flag is the upgrade path — deliberately not built now (YAGNI; "Retired" status covers disposals).
- **SharePoint delete latency:** the outbox drains on pg_cron (≤5 min). The UI reflects deletion instantly from Supabase; SP lags briefly. Same behavior as every other write — acceptable.
- **Open question:** should scanners be able to delete? Plan says no (admin/super_admin only). If branch staff ever need removal powers, widen the RLS policy then.
